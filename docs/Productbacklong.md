# Product Backlog

## Technology and Academic Performance Survey - Product Backlog

### Product Goal

> To build a scalable survey management system using MongoDB, allowing researchers to create questionnaires, manage participants, store responses, and generate analytical reports efficiently.

---

# User Stories

## User Story #1: Register a New Participant

### Description

As a survey administrator,  
I want to register a new participant,  
So that their information can be stored and linked to survey responses.

### Acceptance Criteria

#### Scenario 1: Successful Registration

**Given** the user is in the participants module,  
**When** they enter the participant information,  
**Then** the system must save the data in the `usuarios` collection.

#### Scenario 2: Required Fields Validation

**Given** the registration form is open,  
**When** required fields are left empty,  
**Then** the system must prevent saving and display an error message.

#### Scenario 3: Data Persistence

**Given** the participant was registered successfully,  
**When** the collection is viewed in MongoDB Atlas,  
**Then** the document must appear correctly.

---

## User Story #2: Search Participants by Age

### Description

As a survey administrator,  
I want to filter participants by age,  
So that I can analyze demographic groups.

### Acceptance Criteria

#### Scenario 1: Filter by Age

**Given** the collection contains users of different ages,  
**When** a query is executed by age,  
**Then** only matching participants must be displayed.

#### Scenario 2: Multiple Age Query

**Given** the collection contains users aged 16, 17, and 18,  
**When** the user uses the `$or` operator,  
**Then** all matching records must be returned.

## User Story #3: Search Participant by Email

### Description

As a survey administrator,  
I want to search participants by email,  
So that I can quickly locate a specific user.

### Acceptance Criteria

#### Scenario 1: Direct Search

**Given** the email exists,  
**When** the query is executed,  
**Then** the participant record must be displayed.

#### Scenario 2: Invalid Email

**Given** the email does not exist,  
**When** the query is executed,  
**Then** no results must be returned.

## User Story #4: Manage Survey Questions

### Description

As a survey administrator,  
I want to create and manage questions,  
So that surveys can be updated efficiently.

### Acceptance Criteria

#### Scenario 1: Add Question

**Given** the user is in the questions module,  
**When** they enter question information,  
**Then** the system must store it in the `items` collection.

#### Scenario 2: Filter Required Questions

**Given** questions have a required status,  
**When** a query is executed,  
**Then** only required questions must be displayed.

## User Story #5: Register Survey Responses

### Description

As a participant,  
I want to answer survey questions,  
So that my responses can be recorded.

### Acceptance Criteria

#### Scenario 1: Submit Responses

**Given** the survey form is open,  
**When** the participant selects answers,  
**Then** the system must save them in the `seleccion` collection.

#### Scenario 2: Link Responses

**Given** a response is saved,  
**When** the record is reviewed,  
**Then** it must be linked to the correct participation ID.

---

## User Story #6: Update Survey Questions

### Description

As a survey administrator,  
I want to modify existing questions,  
So that the questionnaire remains updated.

### Acceptance Criteria

#### Scenario 1: Update Question Text

**Given** the question exists,  
**When** the user updates the text using `$set`,  
**Then** the new content must replace the previous version.

#### Scenario 2: Verify Update

**Given** the modification was saved,  
**When** the question is queried,  
**Then** the updated text must be displayed.

---

## User Story #7: Generate Statistical Reports

### Description

As a researcher,  
I want to generate reports using aggregation pipelines,  
So that I can analyze survey results efficiently.

### Acceptance Criteria

#### Scenario 1: Count Participants

**Given** the `usuarios` collection contains records,  
**When** the user executes `$count`,  
**Then** the total number of participants must be displayed.

#### Scenario 2: Group Responses

**Given** the survey contains multiple responses,  
**When** the user executes `$group`,  
**Then** response totals must be generated by question.

---

## User Story #8: Optimize Query Performance

### Description

As a system administrator,  
I want to create indexes on frequently queried fields,  
So that searches execute faster.

### Acceptance Criteria

#### Scenario 1: Create Index

**Given** the `usuarios` collection exists,  
**When** an index is created on `correo`,  
**Then** query execution time must decrease.

#### Scenario 2: Compare Performance

**Given** the query is tested before and after indexing,  
**When** `.explain("executionStats")` is executed,  
**Then** the improvement must be documented in `performance_audit.md`.
